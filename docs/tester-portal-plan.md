# Volunteer tester portal - plan

Status: a plan, not started. Built after the last alpha1 bugs close and before the alpha1 release, together with the
website pass. Nothing here changes the approved look of the download pages (autobleem-repo's CLAUDE.md).

## Goal

Let volunteers test an alpha on their own hardware and tell us what happened, without mailing documents:

1. **test tasks** per platform (PlayStation Classic, Raspberry Pi, PC USB stick, Windows): a platform's plan is cut
   into sections of about 5-10 minutes, and a volunteer is handed one section, not the whole plan. The site hands out
   the section with the fewest passes for the current version, so the coverage fills evenly (target: 3 passes per
   section per platform per version). A section is a checklist, each step OK / problem / not applicable + a comment on
   a problem; the result is saved as one file. The whole plan stays only as a printable PDF;
2. an **issue report form** - platform, version, steps, expected vs actual, optional logs, optional contact;
3. a **daily triage** that sorts new reports into suspected bug / user idea / question / duplicate;
4. an **approve/reject view** in the admin panel: a suspected bug ("pre-bug") becomes a bug only after it is
   reproduced on current develop; then it goes into `docs/bugs.md`, is fixed, and the next alpha ships.

## What exists today

- **The site** (`autobleem.retromenele.pl`): static files in the build server's `autobleem-repo` directory, served
  read-only by Caddy (`docker/repo/`). The pages (`index.html`, `rpi-install.html`, `pc-install.html`, the Store page)
  are generated by `tools/repo_index.py` on every publish with the shared `page_head`/`PAGE_CSS`; nothing on the
  site accepts a write today.
- **The admin panel** (`admin/`): a FastAPI app (fastapi, uvicorn, httpx, pyjwt), one static page, behind
  oauth2-proxy (GitHub login, `autobleem2` org members read, `release-managers` act), every action audited, tests over a
  fake GitHub with a local preview (`admin/tools/dev_server.py`). Its Bugs tab reads `docs/bugs.md` through the GitHub
  App's contents API (`app/bugs_source.py`, parsed by `app/bugs.py`; the App has Contents read **and write**).
- **The hub's data**: `docs/bugs.md` (BUG-N rows: platform, severity, one of four states), `docs/todo.md`, and
  `docs/tester-checklist.md` - today one long Markdown file of numbered steps with Do / Expect columns, written for
  testers but not machine-readable.
- **Logs**: the launcher's Hardware Information -> "Save logs" writes a log folder to the stick; the tester zips it.
- **AI tooling and a schedule**: the build server already runs scheduled jobs (nightly assembly, cleanup) and the
  project has its own AI tooling subscription - no per-request API keys exist or are wanted.

## The parts

### 1. Test plans: one source, two outputs

- **Source**: `testplans/<platform>.yaml` in autobleem-repo (a new folder, reviewed like code): `id`, `title`, and a
  list of **sections** `{id, title, minutes, needs, steps}`; each step is `{id, do, expect, log?}`. `minutes` is the
  honest length of the section (5-10), `needs` is the start state in one line ("a console with AutoBleem and Wi-Fi set
  up", "a stick written with the flasher") so a volunteer knows at once whether they can do it. Ids are stable
  (section `psc-store`, step `psc-store.2`) so results from different versions line up. Example sections for the
  console: install, update, carousel and sets, Store, emulator and in-game menu, memory cards, power off and wake.
  `docs/tester-checklist.md` is split into these files once; afterwards the Markdown is generated from them, or
  retired (the hub points at the site).
- **Task page**: generated by `repo_index.py` next to the other pages - one page per platform, `testing/<platform>.html`,
  that shows **one section** (chosen by the claim, below) in the form below. Plain HTML + a small script (no
  framework): a version box (a dropdown of the channels' current versions, read from `releases/latest.json`,
  `releases/unstable.json`, `nightly/latest.json`; pre-filled from `?v=` when linked from a release), the section's
  title, minutes and `needs` line, then each step with OK / Problem / N/A radios and a comment box that opens only on
  Problem. Progress inside the section is kept in the browser's local storage so a half-filled form survives a reload.
  Submit posts JSON; after it the thanks page offers **Take another task**.
- **Handing out a task**: the landing page shows one card per platform with **Give me a task (~10 min)** and a small
  coverage hint ("most needed now: Store, 1 of 3 done"). The button asks the intake service for a claim (part 2); the
  answer names the section with the fewest passes for the current version (ties: the section with the fewest open
  claims, then the plan's order). There is no login: the browser keeps a random claim id in local storage, and the
  page shows "claimed for you - send it within 48 hours or it goes back to the pool".
- **PDF**: the **whole** plan of a platform (all sections) rendered as a printable sheet (same generator, a print
  stylesheet; the PDF is produced at publish time and linked as "Printable version"). It is the only place the whole
  plan is offered to one person, and it is never the way results come back.

### 2. The intake service

The site is static and read-only, so submissions need one small writer: a second FastAPI service
(`intake/`, same stack and Dockerfile style as `admin/`) behind Caddy at `/submit/*`, mounting **only** its own data
directory read-write (never the site tree). Its endpoints:

- `POST /submit/claim` - JSON `{platform, version, claim?}`; returns `{claim, section, expires}`. Without `claim` it
  assigns the section with the fewest passes (counted from the stored results) for that platform and version; with a
  `claim` that is still open it returns the same section again. A claim is a random id the browser keeps; it is not an
  identity. It expires **48 hours** after it was made if no result arrives, and the section goes back to the pool (the
  expiry is evaluated when claims are read - no timer needed). `POST /submit/claim` with `{claim, release: true}`
  gives a task back, and "Take another task" asks for a new claim (the section just sent counts as a pass, so the
  next one differs);
- `GET /submit/coverage` - the public hint behind the landing cards: per platform and version, the most needed
  section's title and `passes/target`, nothing else (no ids, no reporters);
- `POST /submit/testplan` - JSON `{platform, version, section, claim, steps:[{id,status,comment}], device?, contact?}`;
  validated against the platform's YAML (an unknown section or step id, a step outside the claimed section, a bad
  status or an over-long comment is refused; a result without a valid claim is accepted but counted as unassigned);
  the claim is closed by the result;
- `POST /submit/issue` - multipart: `platform`, `version`, `steps`, `expected`, `actual`, optional `logs` (a `.zip`),
  optional `contact`, `consent_logs` (required when logs are attached), `website` (the honeypot).

### 3. Storage layout (files only, for now)

```
intake/
  testplans/<platform>/<version>/<YYYY-MM-DD>T<HHMMSS>-<id8>.json   # one result = one section
  claims/<platform>/<version>/<claim>.json      # section, made-at, expires-at, closed-by (result id)
  settings.json                                 # {"target_passes": 3, "claim_hours": 48}
  issues/<YYYY-MM-DD>/<id8>/report.json        # the form fields + received time + status
  issues/<YYYY-MM-DD>/<id8>/logs.zip           # only when attached
  triage/<id8>.json                             # the triage verdict (part 4)
  ideas/<id8>.json                              # copies of user ideas, never deleted
```

`<id8>` is a random 8-character id (the reporter is told it, so a follow-up can name it; a public status page looks a
report up by it and shows only its state). `target_passes` (3) and `claim_hours` (48) are settings, not constants. A
pass is a stored result for a section whose steps are all answered; a section with a problem still counts as a pass
and is also listed under problems. Writes are atomic (temp file, rename); nothing is ever edited in place except a
report's `status` field and a claim's closing. Contact data lives only in
`report.json`.

### 4. The daily triage job

- A scheduled job on the project's own build machine (the same scheduler the nightly and cleanup use), once a day,
  through the project's existing AI tooling - no vendor API, no per-request key; if the tooling is unavailable the job
  logs it and leaves the reports `new` (nothing is lost, it retries the next day).
- Input per new report: the report, a short list of recent `docs/bugs.md` titles and earlier reports for duplicate
  matching, the canned-answer index. A log zip is opened read-only, size-limited, and only the launcher's own log
  files are read; log content is treated as untrusted text (never as instructions).
- Output `triage/<id8>.json`: one class - `suspected-bug`, `user-idea`, `question`, `duplicate` - plus a one-line
  summary, a confidence, and the link: a canned answer for a question, the earlier report or `BUG-N` for a duplicate.
- Effects: user ideas are copied to `ideas/` and appear in the User ideas list (kept forever, reviewed when planning
  alpha2); questions get the canned-answer link (shown on the admin view; nobody emails, there is no mailbox); duplicates
  are linked; everything left is the **pre-bug queue**. The job only classifies - it never writes to the hub.

### 5. Admin panel views (new tabs, same stack and auth)

- **Test results**: per platform and version - how many submissions, a matrix of steps by outcome (counts of OK /
  problem / N/A), the problem comments listed under their step, a link to each raw file. Read-only.
- **Coverage**: a matrix of section (rows) by platform (columns) for the chosen version; each cell shows
  `passes / problems` against the target (`target_passes`, 3 by default), coloured when under target, with the
  count of open claims and of claims that expired. It is the view the maintainers use to see which sections still need
  a volunteer. Read-only.
- **Pre-bugs**: the queue with the triage summary, the report, the log download and the possible duplicates. Per
  row, for `release-managers`: **Approve** (= "worth reproducing": it joins a "to reproduce" list for QA), **Reject**
  (with a reason: not a bug / cannot tell / duplicate), **Mark as idea**. Approving does not create a bug. When QA has
  reproduced it on current develop, **Record as bug** appends the next `BUG-N` row to `docs/bugs.md` through the
  contents API (a one-field form: title, platform, severity, linking the report id) and the report's status becomes
  `bug BUG-N`. Reproduction failed = **Reject: not reproduced**. Every decision goes to the audit log.
- **User ideas**: the list of all ideas with the reporter's text and a date; filter by platform; export as Markdown
  for the alpha2 planning. Nothing here deletes an entry.

## Data, privacy and abuse

- **Privacy line** shown next to both forms: "What you send is stored on the project's server, read only by the
  project's maintainers, and used to fix problems and plan the next release; contact details are optional and used
  only to ask about your report. Logs are kept only to investigate the report." A **consent tick** is required to
  attach logs (they can hold Wi-Fi names, game names, device ids). Retention: logs deleted 90 days after the report
  is closed; reports and ideas are kept.
- **Spam**: a hidden honeypot field (a filled one is silently dropped with a normal-looking answer); a rate limit per
  address (for example 5 submissions per hour, 20 per day; the address is held only as a salted hash and only for the
  window); no CAPTCHA service, no third-party script anywhere on the forms.
- **Limits**: body at most 25 MB for an issue with logs, 256 KB for a test result; only `.zip` accepted and opened by
  name with a total-uncompressed-size cap (zip bombs), never extracted onto a path the client names; text fields have
  length caps; output is always escaped in the admin views.
- **Separation**: the intake service has no GitHub credentials and no write access to the site or the hub; the panel
  reads `intake/` read-only and holds the only hub write (the "Record as bug" step, release team only).

## Steps in build order

| # | Step | Size | Alpha1 |
|---|---|---|---|
| 1 | Test-plan YAML format (sections with id, title, minutes, needs, steps); split `tester-checklist.md` into four platform files cut into 5-10 minute sections (content review by the owner) | M | blocking |
| 2 | Intake service: `/submit/claim`, `/submit/coverage`, `/submit/testplan`, `/submit/issue`, validation, storage, claim expiry (48 h), the pass-count rule, limits, honeypot, rate limit, tests; Caddy route + compose profile | M | blocking |
| 3 | Pages generated by `repo_index.py` (the Testing landing with a task card per platform and the coverage hint, the task page for one section, the issue form, the thanks and status-by-id pages, privacy line, consent tick); phone width | M | blocking |
| 4 | Admin: Test results tab and the Coverage matrix (read-only) | S | blocking (without it nobody sees the results or what is still missing) |
| 5 | PDF printable version of the whole plan from the YAML | S | later |
| 6 | Admin: Pre-bugs queue (manual classification first - the owner reads reports without the AI) | M | blocking, minimal: list + approve/reject |
| 7 | Triage job + canned-answer index | L | later (week 1 of alpha1 testing is read by hand) |
| 8 | Admin: User ideas list + Markdown export; auto "Record as bug" into `docs/bugs.md` | M | later (ideas are kept in `ideas/` from day one) |

Parallel: step 1 (content) runs beside step 2 (service); step 3 needs the YAML format from 1 and the endpoint
contract from 2 (agree the JSON shapes first); 4 and 6 need only the storage layout (3 of "The parts") and can start
once it is fixed; 5 and 7 are independent of the forms.

**Alpha1 minimum**: steps 1-4 and the minimal part of 6 - the task hand-out for four platforms, the issue form, storage, the
results view, the coverage matrix and a plain pre-bug list the owner reviews. Triage, PDF, ideas view and the automatic bug record follow
alpha1; until the triage runs, every report simply sits in the list as `new`.

## How it is tested

- Unit tests for the intake service (validation, limits, honeypot, rate limit, claim assignment by fewest passes, claim expiry after 48 h, a result for a section other than the claimed one, atomic writes, zip handling with a
  zip bomb and a path-traversal archive) and for the YAML-to-form/PDF generator, run like the admin suite (a
  `python:3.12-slim` container).
- The pages and both services run on a copy of the site tree and the LAN rig (`http://:9090` plus the intake
  service on the compose network), driven with scripted submissions and a phone-width browser check; the admin
  views through `admin/tools/dev_server.py` with fake data in `intake/`.
- Triage tested first on a fixed set of 30 invented reports (each class, tricky duplicates, a hostile log), checked by
  hand against expected classes before it reads a real report.
- The first real submissions come from the project's own test devices, never from volunteers; volunteers are invited
  only after one full pass of each platform's form by a maintainer.

## Open questions for the owner

1. **Where does the intake service live?** Recommended: on the build server behind Caddy at `/submit/` of the same host
   (one certificate, nothing new to run). The alternative is a separate host name.
2. **Who may read reports and logs?** Recommended: org members read, `release-managers` decide - the panel's existing rule.
3. **Retention of logs**: recommended 90 days after the report closes; reports and ideas kept for good.
4. **Reporter feedback**: with no mailbox, recommended is a public status page by report id ("received / needs more
   info / recorded as BUG-N / not a bug") and nothing else; the alternative is no feedback at all.
5. **Test-plan content**: recommended - the four platforms start from the current `tester-checklist.md` steps, trimmed
   to what alpha1 contains; the owner approves each plan's step list once before volunteers see it.
6. **Do we link the portal from the landing page** or keep it to a "Testing" page reachable only from the alpha
   announcement? Decided: the "Testing" link in the top bar is added only after alpha1 is released.
7. **Tasks, not whole plans** (decided): a volunteer gets one section of about 10 minutes, the one with the fewest
   passes for the current version; the target is 3 passes per section per platform per version (a setting); a claim
   lives in the browser and returns to the pool after 48 hours (a setting); the whole plan stays only as the printable
   PDF. Comments are asked only on a Problem answer. Open: how many sections per platform, and who writes each
   section's `needs` line - the owner approves each platform's section list once before volunteers see it.
